# Understanding (defaults chosen; no open questions)
- "Finalised" sentence: the streaming partials re-transcribe the whole hold every ~0.8 s, so a sentence counts as finalised when it is complete (followed by more speech in the partial) and its text is unchanged in two consecutive partials. Its revision is its text.
- "Long" dictation: at least 2 finalised sentences were sent in the background before release. Anything else is a short dictation and follows exactly today's path (one release call, the existing prompt with plugin routing).
- Background calls use the existing cleanup prompt on one sentence, without the plugin section; at most 2 in flight; one call per sentence revision.
- On release (long path): the remaining raw tail (sentences not cleaned or whose cleaned revision no longer matches) is cleaned in one call. The "quick final pass over the whole text" is a cheap local check for cross-sentence cues; only when a cue is present (scratch that, actually I mean, no wait, I mean, sorry, let me start again / start over, numbered-list cues, an unbalanced spoken quote across sentences) does the release call cover the whole raw text instead (exactly today's full call). This keeps latency down for the common case while catching cross-sentence corrections.
- Gateway failure of a background sentence: that sentence is treated as uncleaned and goes into the release call; a failed release call falls back to local rules for the uncleaned part (cleaned sentences kept).
- Plugin commands: routing stays on the short path; long dictations are dictation (commands are short utterances). The fast-path trigger match still runs on the full transcript first.
- Latency bench: an opt-in Mac test group (env DICTATION_LATENCY_BENCH=1, run by scripts/latency-bench.sh) replays the WAV fixtures in real time through HoldPipeline (the app's audio-input handler) with real whisper and the real gateway from gateway.json, and writes release-to-insert ms to build/latency.json. scripts/test.sh runs it too when DICTATION_LATENCY_BENCH=1.
